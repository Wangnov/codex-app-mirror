# release-manifest.json schema contract

`release-manifest.json` is generated by [`scripts/prepare-release-metadata.sh`](../scripts/prepare-release-metadata.sh)
(stable channel) and by the beta and linux-preview finalize scripts
(`scripts/emergency-finalize-windows-beta.sh`, `scripts/finalize-linux-preview.sh`). It is
published:

- as the stable channel's rolling manifest at
  <https://codexapp.agentsmirror.com/latest/manifest> (and mirrored to the secondary S3
  bucket under `<prefix>/manifest`), and
- as the `release-manifest.json` asset attached to every GitHub Release, on all three
  channels (stable, beta, linux-preview).

[Codex App Manager](https://github.com/Wangnov/Codex-App-Manager) is the primary outside
consumer: its Windows update path
(`crates/codex-win-engine/src/manifest.rs::parse_manifest_for_arch`) fetches the `/latest/manifest`
route and parses `schemaVersion` and `sources.windows`. Today the Manager only ever fetches the
**stable channel**'s `/latest/manifest`; it does not read the `release-manifest.json` GitHub
Release asset directly, and it does not parse `sources.macos` (macOS updates go through the
GitHub Release's `SHA256SUMS-macos.txt` asset instead). See
[`Codex-App-Manager/docs/manifest-contract.md`](https://github.com/Wangnov/Codex-App-Manager/blob/main/docs/manifest-contract.md)
for the Manager-side description of the same contract.

## The schema

[`schemas/release-manifest.schema.json`](../schemas/release-manifest.schema.json) is a
JSON Schema (2020-12) contract for this file. It is deliberately **strict where the Manager
reads a field, and permissive everywhere else**, so additions to the manifest (new upstream
metadata, new `derived.*` bookkeeping, new channels) never break publishing as long as they
don't change or remove a field the Manager already depends on.

Structure:

- The root requires `schemaVersion` (integer) and `sources` (object).
- `sources.linux` being present switches the document into the **linux-preview** branch
  (`$defs/linuxChannelManifest`), which is intentionally loose: the Manager has no Linux
  install path today, so only "it's an object" is enforced. Everything else — stable and
  beta manifests — falls into `$defs/windowsMacosChannelManifest`, which requires
  `sources.windows`.
- `sources.windows` (`$defs/windowsSource`) types every field the Rust parser reads
  (`version`, `appVersion`, `packageMoniker`, `architecture`, `contentLength`, `etag`,
  `lastModified`, `productId`/`updateManifest`, and the `architectures` map) and requires
  that **at least one** of a top-level `packageMoniker` or a non-empty `architectures` map
  is present — mirroring the Rust fallback logic, which fails the parse otherwise.
- Each `sources.windows.architectures.<arch>` entry (`$defs/windowsArchitectureSource`)
  requires `version` and `packageMoniker` **unless** `downloadable` is explicitly `false`
  (catalog-only, rollout-drift, or version-unreadable states legitimately omit or stale
  those fields — the mirror pipeline's own fixtures rely on this).
- `sources.macos` is typed but loosely (not Manager-consumed today; kept for forward
  compatibility with `Codex-App-Manager/docs/manifest-contract.md`).
- `derived`, `publication`, `beta`, `preview`, `release`, and every other top-level or
  nested block not listed above is left fully open (`additionalProperties: true`
  everywhere), including on the two branches above.

## Fixtures

[`schemas/fixtures/`](../schemas/fixtures/) holds real and fixture-generated samples, grouped
by channel (`stable/`, `beta/`, `linux-preview/`), plus `invalid/` for negative cases the
validator must reject. `stable/` includes both live production releases (schemaVersion 5) and
manifests produced by `scripts/test-prepare-release-metadata.sh`'s edge cases (ARM64 rollout
drift, ARM64 preserved-from-latest, missing backend version). `beta/` holds a real historical
GitHub Release asset (schemaVersion 1, predating the current `channel`/`publication` beta
contract) — it is still real, still on the release page, and still expected to validate.
`linux-preview/` holds a real GitHub Release asset (schemaVersion 6) and one produced by
`scripts/test-linux-preview-publish-release.sh`.

Every file under `stable/`, `beta/`, and `linux-preview/` **must** validate; every file under
`invalid/` **must not**.

## Validating

[`scripts/schema/`](../scripts/schema/) is a tiny Node package (ajv + ajv-formats, exact-pinned,
with a `package-lock.json`) that compiles the schema and validates one or more manifest files:

```bash
node scripts/schema/validate.js schemas/release-manifest.schema.json path/to/release-manifest.json
```

[`scripts/test-release-manifest-schema.sh`](../scripts/test-release-manifest-schema.sh) runs the
full fixture suite (all positive fixtures, then all `invalid/` fixtures with
`--expect-invalid`) and is wired into `.github/workflows/ci.yml`.

## Fail-closed publishing

`.github/workflows/mirror.yml`, `.github/workflows/beta-prerelease.yml`, and
`.github/workflows/linux-preview.yml` each validate the `release-manifest.json` they just
generated — right after the "Prepare/Finalize" step and before any asset is uploaded,
published, or synced to object storage. A schema violation fails the workflow before it
publishes anything. Because `mirror.yml` runs on a 15-minute schedule, this step is kept to a
single `npm ci` (cached by the lockfile) plus one `node` invocation, so it only fails on an
actual contract violation, not on drift or flakiness.

## Versioning rule

`schemaVersion` is a flat integer, bumped whenever a **field the Manager consumes** changes
incompatibly (renamed, retyped, or removed — not when a field is only added). The Manager's
own rule (`crates/codex-win-engine/src/manifest.rs`) is `schemaVersion >= 2`; this JSON Schema
only requires `schemaVersion >= 1` so that older, still-published GitHub Release assets
(such as the schemaVersion-1 beta fixture above) keep validating as *structurally sound*
historical documents, even though the Manager itself would refuse to parse them. When you
change a Manager-consumed field:

1. Bump `schemaVersion` in the script(s) that emit it (`prepare-release-metadata.sh`,
   `emergency-probe-windows-beta.sh`, `probe-linux-preview.sh`, …).
2. Update `schemas/release-manifest.schema.json` to describe the new shape (add a new
   required/typed field, or relax one that's being removed).
3. Add or update a fixture under `schemas/fixtures/` that exercises the new shape, and a
   negative fixture under `schemas/fixtures/invalid/` if the old shape should now be rejected.
4. Update the Manager's parser and its own contract doc in the same PR cycle if the change
   is breaking (coordinate — the Manager pins a minimum `schemaVersion` and fails closed on
   older values).
